## 优化

现在到Meyers（局部静态变量）已经是单例的最终形态。基于单例之上还有优化点：

- 因为是懒加载，且析构顺序是构造逆序，对于它依赖的和依赖它的单例类，可以在main函数中显式调用来定序
-

| 痛点 | 传统 Meyers 单例表现             | 现代替代思路                     |
| ---- | -------------------------------- | -------------------------------- |
| **单元测试难 Mock**     | 全局状态，无法替换               | 依赖注入（DI）+ 接口抽象         |
| **隐式耦合/生命周期不可控**     | 析构顺序依赖调用顺序             | 显式服务容器 / 工厂模式          |
| **多线程首次调用性能损耗**     | 有一次同步开销（通常 <50ns） | 启动期预初始化（`instance()`在`main()`早期调用一次） |

## 编译

```cpp
class Singleton{
public:
    Singleton(const Singleton&) = delete;
    Singleton & operator = (const Singleton&) = delete;

    static Singleton & instance(){
        static Singleton instance;
        return instance;
    }
private:
    Singleton() = default;
};

```

我们将默认构造设置为 `private` 并且显式 `delete` 拷贝构造和赋值运算符，这样的话用户只能通过 `instance` 这个函数来获取我们预先创建好的对象，不能自己通过构造函数创建一个对象。而使用静态局部变量是为了保证这个变量的初始化线程安全。

如何确保单例唯一呢？

> 在 Linux 上就很简单了，如果同一个变量出现在**<u>多个动态库</u>**中，只要确保这些动态库都把这个符号设置为对外可见就行了。而**编译器默认的行为也就是对外可见**，所以基本上不用担心这个问题。

> 在 Windows 上呢？非常麻烦了，必须要**确保只有一个 dll 使用** **`dllexport`** **导出了这个符号，其他所有的** **`dll`** **必须要使用** **`dllimport`**。这件事情常常不太好做，你可能写着写着就忘记，是哪个 dll 负责导出的这个符号了。怎么办呢？那就是**专门用一个 dll 来管理所有的单例变量**，也就是说这个 dll 负责 `dllexport` 所有的单例变量，除此之外的 dll 都只 dllimport 就行了。之后添加和修改都在这个 dll 中进行，这样就比较好管理了。

## 普通全局变量 和 单例 辨析

### 初始化机制

编译器将非平凡构造函数的调用地址收集到特殊段（如 ELF 的 `.init_array` 或 PE 的 `.CRT$XCU`）。程序启动时，C 运行时（`crt0.o`）遍历该数组依次调用。
⚠️ 若多个**翻译单元（TU）** 的全局变量存在依赖，构造顺序**未定义**，即著名的 *Static Initialization Order Fiasco*。

> 发现非平凡函数引申很多东西，另开一篇[平凡与非平凡构造函数辨析](/posts/trivial-nontrivial-constructors/)
>
> 很幸运在编译原理的漫游让我能勉强看懂**段**，感恩当时的自己。
>
> **TU**：一个 `.c` 或 `.cpp` 源文件，经过**预处理器**处理（展开所有 `#include`、`#define`、条件编译等）后，形成的完整、自包含的源代码文本。
>
> C++20 引入了 `import` 和模块机制，**打破了传统 TU 的文本包含模型**。模块只导出声明和已编译的语义信息，不再物理展开头文件，从而大幅减少重复编译和宏污染。但传统 `#include` + TU 模型仍广泛兼容并使用。


编译器**不会**在启动期生成初始化调用。而是将对象分配在该函数的静态存储区，并生成一个隐藏的**守卫结构体（Guard Variable）** 。函数入口被改写为类似逻辑：

```cpp
// 编译器生成的伪代码（概念级）
if (!guard.initialized) {
    if (__guard_acquire(&guard)) {
        new (&storage) QtSpdlogBridge(); // 原地构造
        __guard_release(&guard);
    }
}
return reinterpret_cast<QtSpdlogBridge*>(&storage);
```


> 如果有多个线程同时初始化，如何保证构造函数只调用一次？
>
> 编译器会围绕这个对象构建一个**状态机**：编译器会在**静态存储区**（通常是 `.data` 或 `.bss` 段，**编译阶段就确定了它们在内存中的偏移量**）为这个静态变量分配空间，并额外申请一个**守卫变量**（通常是一个 64 位的整数）。当对象还未初始化时，守卫变量值为0；正在初始化，为某特定值；初始化完成，值为1。
>
> 大概逻辑就是，先原子读取检查一下有没有初始化（**双重检查锁**），如果没有，加锁，其他初始化线程阻塞，执行构造函数，标记守卫为1，唤醒其他线程，然后catch异常，如果构造失败重置守卫。


但是**全局变量不要求启动期多线程安全，行为未定义**。

编译器实现通常如下：

| 编译器    | 守卫机制                  | 现代优化                               |
| --------- | ------------------------- | -------------------------------------- |
| GCC/Clang |  **`__cxa_guard_acquire/release`**（基于 futex 或原子操作） | C++11 起使用 **`__atomic`**实现无锁双重检查           |
| MSVC      | `Init_thread_header / _foot / _abort`                          | 基于`INIT_ONCE`API 或 **CAS**（发现去年这时候就学过woc） |

后续调用中，守卫检查被优化为单条原子加载或完全消除（若编译器证明不可能并发）。

### 符号可见性和连接行为

**全局变量**：默认具有 `external linkage`。**链接器会在符号表中记录其地址**，允许其他 TU 通过 `extern` 引用。需严格遵守 ODR（One Definition Rule）。

**单例**：函数内的 `static` 变量**没有链接（no linkage）** 。编译器会为其生成内部名称（如 `_ZL8instance` 或带哈希的局部符号）。
天然避免符号冲突；即使函数被内联到多个 TU，链接器也能通过 **COMDAT** 或**弱符号**保证全局唯一。

### 析构注册与生命周期控制

- 两者都在程序退出时析构，但注册时机不同：

  - 全局变量：构造完成后立即由**启动代码注册到** **`atexit`** **链表**。
  - Meyers 单例：**首次构造完成后**才由编译器插入的代码调用 `std::atexit` 注册析构函数。
    这意味着：如果某个 TU 的 `main()` 提前调用 `std::exit()`，而单例从未被调用，则**不会执行析构**（文件句柄未关闭、日志未 flush）。

###  编译器优化差异

| 场景           | 全局变量                          | Meyers 单例                                          |
| -------------- | --------------------------------- | ----------------------------------------------------- |
| `constexpr`/`constinit`              | 可编译期求值，放入`.rodata`             |  延迟初始化无法参与常量求值（除非 C++20 特殊限制） |
| 跨函数内联优化 |  编译器可常量传播、消除重复访问 |  首次调用含控制流，阻碍部分优化                    |
| 后续访问性能   | 直接寻址`mov eax, [global_addr]`                          | 首次守卫检查后，编译器优化为直接返回静态地址，**后续与全局变量无差异**       |

### 实际编译产物观察（以 GCC/Clang 为例）

用 `nm` 或 `objdump` 查看符号表可直观看出差异：

```bash
# 全局变量
0000000000004020 B g_logger      # 在 .bss，全局可见

# Meyers 单例（函数内 static）
0000000000004030 b _ZZL8instanceE.s_instance  # b = 局部静态，隐藏符号
0000000000004028 b _ZZL8instanceE.guard       # 守卫变量
```

函数内部会多出守卫检查的分支指令，但现代编译器在 `-O2` 及以上会将**守卫检查内联为极短的原子操作序列**。

编译器对全局变量采用"启动期批量注册+直接地址访问"的**静态策略**；对 Meyers 单例采用"函数内延迟触发+编译器插桩守卫协议"的**动态策略**。**两者存储期相同，但初始化时机、同步保障、符号可见性及运行时控制流截然不同。** 现代 C++ 中，除非明确需要启动期就绪，否则Meyers 单例是编译器处理更安全、更可预测的选择。
